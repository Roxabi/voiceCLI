## Problem

Lyra currently reaches voiceCLI via per-host Unix-socket daemons (`voicecli tts-serve` / `voicecli stt-serve`), which couples the two projects to the same machine and to a bespoke newline-JSON protocol. ADR-044 (frozen in Roxabi/lyra#688) replaces that with a NATS-only message bus: lyra publishes requests on `lyra.voice.{stt,tts}.request`, voice workers reply on a per-request inbox, and workers advertise liveness on `lyra.voice.{stt,tts}.heartbeat`. This issue is the voiceCLI side of that decoupling — without it, the Machine-1 cutover in Roxabi/lyra#689 cannot start.

Observable impact today: voiceCLI and lyra must be co-deployed, adding capacity requires socket multiplexing hacks, and there is no standard way for lyra to discover healthy workers or retry a failed transcription on a sibling GPU.

## Who

- **Primary:** voiceCLI operators deploying worker processes on GPU hosts (roxabituwer prod, roxabitower dev) who currently run `tts-serve`/`stt-serve` under supervisord. They need a second serve mode they can enable alongside the existing one.
- **Secondary:**
  - Lyra hub (Roxabi/lyra#658) — consumer of the NATS contract; blocked on this entry point being deployable.
  - Future voice workers on additional machines — scaling out is gated on the queue-group / competing-consumer semantics this PR introduces.

## Constraints

- **Schema frozen by ADR-044 / Roxabi/lyra#688** — request/reply fields and `contract_version` must match exactly. Changes require an ADR revision, not a silent drift.
- **Subjects:** `lyra.voice.stt.request`, `lyra.voice.tts.request`, `lyra.voice.{stt,tts}.heartbeat`. Queue group for competing consumers.
- **Heartbeat cadence ≤ 5 s** with at minimum `{worker_id}`; optional `model_loaded`, `vram_used_mb`, `vram_total_mb`, `active_requests`.
- **Auth:** NATS nkey seed — reuse existing lyra nkey provisioning pattern (env vars `NATS_URL`, `NATS_NKEY_SEED_PATH`).
- **Engine selection:** `LYRA_TTS_ENGINE` env var drives default engine; per-request `engine` field may override.
- **Coexistence:** the existing `voicecli tts-serve` / `voicecli stt-serve` Unix-socket daemons MUST keep working unchanged. This PR is additive; the lyra-side cutover happens in Roxabi/lyra#689.
- **E2E test gate:** docker-compose bringing up NATS + lyra hub (main) + `voicecli nats-serve` must pass a voice round-trip.
- **`--all-extras` install path** continues to work (the `nats` dependency must land in an extras group compatible with that install flow).
- **VRAM budget on RTX 3080 (10 GB)** — TTS daemon ~7.4 GB, STT daemon ~2.2 GB. Any new worker sharing that GPU must not break existing OOM-avoidance patterns documented in CLAUDE.md.

## Out of Scope

- Removing or deprecating `voicecli stt-serve` / `voicecli tts-serve` (Unix-socket daemons) — they stay until Roxabi/lyra#689 cutover completes.
- Lyra-side producer changes (tracked in Roxabi/lyra#658 / #689).
- ADR-044 schema changes — the contract is frozen; this PR implements it verbatim.
- Supervisord program config for the new serve mode (deploy concern, separate change in `~/projects/lyra-stack` or voiceCLI deploy docs).
- Auto-cutover logic (lyra choosing NATS vs Unix socket) — lyra's problem.
- Multi-host orchestration, leader election, or queue rebalancing beyond what NATS queue groups give for free.

## Complexity

**Tier: F-full** — new integration surface (NATS subscriber + publisher + heartbeat loop), cross-project contract with frozen schema, docker-compose E2E harness, and coexistence requirements with two existing daemons. Analysis step is worth running to inventory reusable patterns from `stt-serve`/`tts-serve` (lifecycle, engine loading, VRAM discipline) and to pin the exact schema fields from ADR-044 before spec.

Signals observed:
- Multi-domain: CLI (Typer), engine API, new messaging layer, test infra (docker-compose).
- New architectural pattern in voiceCLI: message-bus subscriber (vs. existing socket/Unix-daemon patterns).
- Cross-project contract with frozen ADR — correctness risk if fields are misread.
- E2E test requires external services (NATS broker, lyra hub) — new CI/test harness.
- Blocks a downstream migration (lyra#689), so regression on the existing daemons would cascade.
