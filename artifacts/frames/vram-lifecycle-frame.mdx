## Problem

On the production RTX 3080 (10 GiB), the TTS daemon (`qwen-fast`) and Whisper STT compete for VRAM with no coordination or cleanup, leading to cascading OOM failures.

**CUDA memory growth**: The TTS daemon starts at ~5.8 GiB but PyTorch accumulates intermediate tensors, CUDA graph allocations, and reserved-but-unallocated memory over time — growing to ~7.3 GiB (observed in production logs). There is no periodic `torch.cuda.empty_cache()` to reclaim this overhead. The ~1.5 GiB of growth is enough to push the system over the edge.

**STT daemon can't start**: `voicecli_stt` does an eager warmup (loads Whisper `large-v3-turbo` into VRAM at startup). When the TTS daemon already holds 5.8+ GiB and Lyra has loaded its own Whisper fallback (2.3 GiB), there's no room — the daemon crashes in a loop and goes FATAL.

**Duplicate Whisper loading**: Lyra's `STTService` calls `voicecli.transcribe.transcribe()` which is daemon-first (tries the Unix socket, falls back to local `_load_model()`). When the STT daemon is down (FATAL), Lyra loads Whisper into its own process — 2.3 GiB stuck in a module-level `_model_cache` with no unload mechanism. Even if the daemon comes back later, the local model stays in VRAM forever.

**Observed impact** (2026-03-28/29 production):
- TTS failed repeatedly with OOM on `qwen-fast` (7.3 GiB PyTorch + 2.3 GiB other process = 9.6/9.64 GiB)
- Voice message transcription failed — Whisper couldn't load
- STT daemon stuck in FATAL (4 failed warmup attempts → supervisor gave up)

## Who

- **Primary:** Mickael — only user of Lyra on Telegram, sends voice messages and expects TTS responses
- **Secondary:** Any future multi-user scenario on the same GPU

## Constraints

- RTX 3080 = 10 GiB VRAM, non-negotiable hardware on production (24/7 server)
- Models must stay hot — no idle timeout. Cold start for qwen-fast is ~60s, unacceptable for conversational flow
- TTS daemon and STT daemon are separate supervisor processes (can't share a Python process)
- Lyra imports `voicecli.transcribe` as a library (in-process), not via daemon socket for STT
- The daemon-first pattern in `transcribe()` already exists — the plumbing is there, just missing lifecycle primitives

## Solution Axes

### 1. Periodic VRAM cleanup in TTS daemon

Add a `torch.cuda.empty_cache()` + `gc.collect()` call in the TTS daemon worker loop — either after every N requests or on a timer. This reclaims the ~1.5 GiB of PyTorch overhead without unloading the model. The model weights stay in VRAM, only fragmented/cached allocations are freed.

### 2. `unload_model()` API in `voicecli.transcribe`

Expose a function that clears `_model_cache`, deletes model references, and calls `torch.cuda.empty_cache()`. This lets Lyra release its local Whisper when it no longer needs it (e.g., when the STT daemon becomes available).

### 3. STT coordination: Lyra yields for the daemon

When the STT daemon starts (or Lyra detects the daemon socket appears):
1. Lyra calls `unload_model()` to free its local Whisper (~2.3 GiB)
2. The daemon loads Whisper in its own process
3. Subsequent `transcribe()` calls go through the daemon socket

Ideally, Lyra should also be able to **proactively unload and wait** — pause STT processing, free VRAM, let the daemon start, then resume via daemon.

### 4. Startup ordering

Supervisord starts all processes at once. The STT daemon's eager warmup races with Lyra's first voice message. Fix options:
- STT daemon: lazy warmup instead of eager (load on first request, not at startup)
- Supervisor: `priority` ordering so STT daemon starts before Lyra
- STT daemon: retry warmup with backoff instead of crashing after 3 attempts

## Out of Scope

- Changing production GPU hardware
- Model quantization (int8/int4) — separate optimization
- Splitting TTS and STT across different GPUs
- Idle timeout / model unloading for TTS (user wants models hot)

## Complexity

**Tier: F-lite** — Clear scope across two repos (voiceCLI + Lyra), single domain (VRAM lifecycle), known patterns to implement. No new architecture, but cross-project coordination needed.

Signals:
- voiceCLI changes: VRAM cleanup in daemon + unload API in transcribe (~2 files)
- Lyra changes: STT service calls unload when daemon is detected (~1 file)
- Supervisor config: startup ordering (~1 file)
- Multiple repos but well-bounded scope
